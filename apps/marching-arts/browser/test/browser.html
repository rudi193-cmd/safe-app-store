marching-arts — the checks Node cannot run

These four are now automated. npm run test:browser drives all of them in a headless Chromium and npm run test:browser:mutation breaks each one to prove the checks can fail. Both run in CI as the browser-mechanisms job. This page is kept for looking at a mechanism by hand, and for driving the two-tab cases interactively — it is not the gate.

Serve this directory over http (npm run serve, then 127.0.0.1:8177/test/browser.html). Not file://: a null origin has no OPFS. That server also rewrites the one bare import specifier dist/ uses, which a browser cannot resolve on its own — any other static server will 404 on @sqlite.org/sqlite-wasm.

Everything below runs in a worker, not on this page. FileSystemFileHandle.createSyncAccessHandle() is [Exposed=DedicatedWorker], so installOpfsSAHPoolVfs() on the main thread fails with “Missing required OPFS APIs.” and openDatabase() silently returns the memory rung. An earlier version of this page called it directly and reported vfs = memory forever, which read as a broken pool rather than as the wrong thread.

What a pass here means

1  the SAH pool installed and a database opened on it: durability is real
2  the P1 gate holds against a file, not only against :memory:
3  every tab shares one owner — but see the note below about what that owner is on
4  the pool was released and retaken without corruption: pauseVfs/unpauseVfs work

On button 3, expect vfs=memory durable=false, and that is not a bug in this page. A SharedWorker is not a DedicatedWorker, so it cannot create sync access handles either; the shared owner gives uniqueness without durability on this engine.
