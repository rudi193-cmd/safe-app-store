StorySession

The reader that plays a world — and never keeps it.

Every part already exists; only the reader is new. StorySession is a GameSession like the other three — so it runs on the-table's driver and ledger unchanged. What makes it a story is that it reads a world out of the flagship Knowledge OS as plain atoms, plays it through the spine, and then forgets the play. Only two things can outlast a session, and a person authors both.

01

The mechanism

Read the world as atoms · play it · forget it · and let a person make two things persist.

02

It's a GameSession — so the spine is free

The same seven methods the other three adapters implement. No new driver, no new ledger.

StorySession(store, uuid, timeline_id) — implements the pinned GameSession
reset(seed)          # open: load the timeline's scenes + its entities from the store
current_seat()       # whose turn — a player, or the table
observe(seat)        # what this seat can see — fog of knowledge (the-binder)
legal_moves(seat)    # the approaches this beat: Grit · Weird · Cute · Cool
step(seat, move)     # resolve via Engine.roll (2d6), narrate, advance the scene
is_terminal()        # the timeline's scenes are played out
result()             # how the story went — a summary, not a winner

04

What can outlast the session

Exactly two things — and a person authors both. Everything else is played and let go.

machine proposes · person seals

Seal a fact into the vault

A canon-worthy outcome is proposed during play; the person at the head of the table SEALS it — or leaves it PENDING, the way the Silver Compass hook waits for a human. It lands in ai-game-master: sealed, append-only, un-retconnable.

the play grows the world

Promote a scene to the timeline

A fact the table established becomes a new timeline_entry in story-timeline — written back with put() and a derived_from: this session edge, so the world remembers where it came from.

What is never written: the players. No attendance, no per-person record, nothing a child couldn't erase. The reader forgets the play by design — only the world's canon can persist, and only when a person seals it. The room with no ledger, made structural.
05

The laws it already obeys

None of these are new rules for this design. Each is a decision the house already sealed.

✔
Ship the reader; the world stays in a box. — the sealed corpus decision: “the capability travels, the wood stays.” The reader is the shippable part; the atoms never leave the writer's box.
✔
The machine proposes; only a person seals. — the fleet canon covenant ai-game-master enforces. StorySession offers; a named human at the table disposes.
✔
The room with no ledger — a memory that forgets on purpose. — the Homestead Table principle. The living play is attested by being played, then let go.
06

Built vs. new

The design is mostly wiring. The only code we write is the reader and its two seams.

Already built — reused

  • story-timeline — the world (scenes, tensions, provenance)
  • the-binder — entity recognition (fog of knowledge)
  • ask-jeles — lore retrieval
  • apps/game — Engine.roll resolution (2d6)
  • the-table — the protocol, driver & ledger
  • ai-game-master — the sealed canon vault

New — the only code

  • StorySession — the reader: a GameSession over a story-timeline world read as atoms
  • the propose→seal seam to the vault
  • the promote→timeline seam back into the world
This is the design, drawn before any code — one page so the shape can be argued with before it's built. It closes the store's own gap E3 (“integrations are narrative-only… a story, not a system”) with the first real pipeline across the flagship Knowledge OS — and it does it the store-native way: through shared atoms, not code that wires apps together. The world in a box; the reader shipped; the play let go.
